# AGENTS.md

## Назначение

Этот репозиторий — тестовое задание по накоплению материала на регулярной поверхности Unity. Любой агент или разработчик должен довести конкретный шаг до проверяемого результата, не разрушая инженерные гарантии проекта.

Главный технический источник правды — `PROJECT.md`. Этот файл задаёт правила работы. Пользовательские инструкции имеют приоритет. Если реализация требует изменить зафиксированное решение, сначала обновите «Журнал решений» в `PROJECT.md` и кратко объясните компромисс.

## Текущая платформа

- Unity `6000.3.10f1`.
- URP `17.3.0`.
- Input System `1.18.0`.
- C#, API compatibility текущего Unity-проекта.
- Основная демо-платформа: Windows и клавиатура.

Не меняйте версию Unity, render pipeline или набор packages без доказанной необходимости. Сторонние реализации генерации/деформации геометрии запрещены. Стандартные компоненты и официальные Unity packages допустимы, но новая зависимость должна решать реальную задачу.

## Неприкосновенные продуктовые инварианты

1. Накопленный материал хранится в отдельном height field, не в Mesh.
2. Высота монотонна и может уменьшиться только при явном Reset.
3. Нет GameObject, Mesh или renderer на отдельные порции/штампы материала.
4. Движущийся brush обрабатывает весь отрезок между прошлым и текущим состоянием.
5. Временные веса подшагов в сумме равны исходному `deltaTime`; число stamps не ускоряет накопление.
6. Радиус интерполируется вдоль sweep и ограничивает только добавление новой высоты.
7. Ранее созданный материал переживает движение и уменьшение радиуса.
8. После прогрева в непрерывном runtime-цикле нет managed allocations.
9. Reset очищает Core-состояние, после чего Mesh синхронизируется из него.
10. Core компилируется и тестируется без `UnityEngine`.

Если изменение нарушает любой пункт, оно не готово.

1. Прочитайте полностью `PROJECT.md`, затем этот файл.
2. Проверьте `git status --short` и последние содержательные коммиты.
3. Осмотрите связанные файлы и asmdef до редактирования.
4. Не перезаписывайте и не откатывайте чужие незакоммиченные изменения.
5. Сформулируйте минимальный проверяемый результат текущего шага.
6. Если задача затрагивает архитектуру, сначала сверьте направление зависимостей.

Не начинайте «рефакторинг заодно». Смежная правка допустима, только если без неё нельзя безопасно завершить запрошенный шаг.

## Разрешённая структура зависимостей

```text
PromVR.MaterialAccumulation.Core
    references: System/BCL only

PromVR.MaterialAccumulation.Unity
    references: Core, UnityEngine, Input System, URP only where needed

PromVR.MaterialAccumulation.Tests.EditMode
    references: Core, NUnit/Unity Test Framework
```

- Core не знает о `MonoBehaviour`, `Mesh`, `Vector3`, `AnimationCurve`, `Time`, Input System, сценах или asset-ах.
- Unity-слой преобразует координаты, владеет ресурсами и вызывает Core.
- View читает height field и dirty region, но не решает, сколько материала добавить.
- Input/preview не изменяют массив высот напрямую.
- Не используйте singleton, service locator, статическое глобальное состояние или поиск зависимостей через `Find*` в рабочем цикле.
- Не вводите интерфейс, фабрику или DI framework без второй реальной реализации/границы тестирования.

Предпочтительная простота: маленькие конкретные Core-типы, явные конструкторы и несколько узких Unity-адаптеров.

## Правила Core

### HeightField

- Единолично владеет заранее выделенным `float[]`.
- Не возвращает изменяемый массив публично.
- Индексация row-major: `z * width + x`.
- Размеры и cell size валидируются в конструкторе.
- Запись высоты централизована и сохраняет `height >= 0`.
- `Reset` использует существующее хранилище и помечает полную область dirty.

### Накопление

Формула stamp должна сохранять монотонность:

```text
ceiling = sqrt(radius² - distance²)
candidate = min(oldHeight + rate * sampleTime, ceiling)
newHeight = max(oldHeight, candidate)
```

- До `sqrt` сначала проверяйте `distanceSquared < radiusSquared`.
- Не нормализуйте расстояние и не вызывайте `sqrt` для ячеек вне диска.
- Перебирайте только ограниченный AABB stamp-а.
- Clamp индексов выполняется до циклов.
- Dirty rect расширяется только при фактическом изменении значения.
- Не скрывайте численные допуски: именуйте константу и объясняйте её необходимость.

### Sweep

- Начало и конец берутся из последовательных состояний одного кадра.
- Число сегментов определяется и перемещением, и изменением радиуса.
- Максимальный spatial/radius step привязан к минимальному cell size.
- Для движущегося sweep применяйте трапецеидальные веса концов.
- Для полностью статичного состояния применяйте один stamp с полным временем.
- При выключенном накоплении обновляйте прошлое состояние без stamp-а.
- Не вводите молчаливый лимит подшагов, способный оставить дыру. Если нужен safety budget, это отдельное документированное продуктовое решение с тестом поведения.

## Правила Unity-слоя

### Жизненный цикл

- Runtime Mesh создаётся один раз, получает понятное имя и `MarkDynamic()`.
- Созданный Mesh уничтожается владельцем в `OnDestroy`.
- Любой `NativeArray` с persistent allocator освобождается ровно один раз.
- Компоненты корректно переживают disable/enable и повторный Play Mode.
- Ошибочная конфигурация обнаруживается в `OnValidate` и проверяется при инициализации.
- Логи ошибок не повторяются каждый кадр.

### Координаты и время

- Simulation получает секунды и локальные метры, а не неявные frame units.
- Movement использует `speed * deltaTime` и нормализованный input vector.
- Brush center переводится в локальный XZ поверхности явно.
- Используется `Time.deltaTime`, если дизайн не переведён целиком на фиксированный simulation tick.
- `AnimationCurve` вычисляется только в Unity-слое; Core получает готовые радиусы.
- Radius curve clamp-ится к `[0, 1]`, радиус — к валидному положительному диапазону.

### Mesh

- Топология, indices и UV создаются только при инициализации/явной смене resolution.
- Рабочий цикл использует постоянный vertex buffer.
- Обновляется dirty region; область нормалей расширяется на одну ячейку.
- Bounds известны заранее из валидированного диапазона радиуса.
- Не вызывайте каждый кадр `mesh.vertices`, `RecalculateNormals`, `RecalculateBounds`, `UploadMeshData(true)` или перестроение triangles.
- `MeshUpdateFlags` применяются только когда инварианты действительно позволяют пропустить соответствующую работу Unity.
- При количестве вершин больше 65 535 выбирайте 32-bit index format до установки indices.
- Не обновляйте MeshCollider каждый кадр в базовой реализации.

### Preview и сцена

- Preview полусферы — один постоянный объект/mesh, не часть накопленного состояния.
- Материал поверхности — один renderer, допустимо отдельное статичное основание.
- Runtime-иерархия не должна расти.
- Не редактируйте `.unity`, `.prefab` и `.asset` как обычный YAML, если ту же операцию безопаснее выполнить Editor API или Unity Editor.
- Любой новый Unity asset коммитится вместе со своим `.meta`.

## Правила производительности C#

В `Update`, stamp/sweep, dirty mesh update и preview update запрещены без измеренной необходимости:

- LINQ;
- создание массивов, списков, enumerator-объектов, делегатов и замыканий;
- интерполяция/форматирование строк и per-frame logging;
- boxing value types;
- `GetComponent`, `Find*`, `Camera.main` и material instantiation;
- чтение свойств Mesh, возвращающих копии массивов;
- создание/уничтожение Unity objects.

Разрешены заранее выделенные массивы, простые циклы, value types и повторно используемый `MaterialPropertyBlock`. Кэшируйте ссылки при инициализации.

«0 B/frame» относится к steady state после прогрева. Инициализационные аллокации допустимы и должны быть отделены в профилировании. Не жертвуйте корректностью ради гипотетической оптимизации; сначала профилируйте.

## Стиль кода

- Используйте namespace `PromVR.MaterialAccumulation.*`.
- Один основной тип на файл; имя файла совпадает с типом.
- Классы `sealed`, если наследование не является контрактом.
- Inspector: `[SerializeField] private`, единицы измерения отражены в имени или tooltip.
- Не выставляйте поля публичными ради Inspector.
- Не используйте magic numbers; spatial step и tolerance имеют именованные значения.
- Публичные методы узкие: `ApplySweep`, `Reset`, чтение размеров/высоты по контролируемому API.
- Комментарий обязан отвечать «почему», особенно для трапецеидальных весов, dirty normal border и монотонного `max`.
- Избегайте regions и чрезмерной вложенности; ранний выход предпочтительнее.
- Не добавляйте абстракции «на будущее», перечисленные только в разделе улучшений.

## Тестовый контракт

Каждое изменение математики сначала или одновременно получает Core-тест. Минимальный обязательный набор перечислен в `PROJECT.md`, раздел 12.

Особенно нельзя сдавать без тестов:

- монотонность при меньшем ceiling;
- ограничение высоты полусферой;
- повторное/пересекающееся накопление;
- временная сумма подшагов;
- быстрый непрерывный sweep;
- различное кадровое разбиение одного движения;
- границы сетки;
- reset.

Тесты должны проверять наблюдаемое поведение, а не приватную реализацию. Для float используйте осмысленный tolerance, связанный с grid/time discretization. Не ослабляйте tolerance только ради зелёного теста — сначала объясните ошибку аппроксимации.

После изменения Unity view выполните ручной smoke test сцены даже при зелёных Core-тестах.

## Проверка перед завершением шага

Выполните доступный максимум:

1. Проверка форматирования/диффа: `git diff --check`.
2. Проверка статуса: `git status --short` — только ожидаемые файлы.
3. Компиляция проекта Unity без новых Console errors.
4. Edit Mode tests.
5. Для runtime-изменений — Play Mode smoke test.
6. Для performance-изменений — Profiler после прогрева, без Deep Profile.
7. Для сцены/ввода — standalone build smoke test перед финальной сдачей.

Не завершайте пользовательский Unity-процесс и не обходите lock проекта. Если проверка недоступна, явно сообщите, что именно не запускалось и почему.

## Git и файловая гигиена

- Не коммитьте `Library/`, `Temp/`, `Logs/`, `UserSettings/`, builds, profiler captures и IDE caches.
- Не используйте destructive reset/checkout для чужих правок.
- Не меняйте import settings массово без необходимости.
- Перед коммитом просмотрите полный diff и список untracked файлов.
- Один коммит представляет один проверяемый архитектурный шаг.
- Сообщение описывает результат, а не действие вроде `changes`, `work` или `fix`.
- Не создавайте пустые/WIP-коммиты ради красивого количества.
- Не переписывайте уже опубликованную историю без явного запроса пользователя.
- Создавайте коммит только если пользователь запросил коммиты или текущий автономный этап явно включает ведение истории; иначе оставьте проверенный diff и предложите точное сообщение.

Ориентир последовательности коммитов находится в `PROJECT.md`, раздел 13. Он не является требованием искусственно разделять тесно связанную реализацию.

## Definition of Done для любого изменения

- Изменение решает заявленную задачу и не расширяет scope без причины.
- Архитектурное направление зависимостей сохранено.
- Продуктовые инварианты не нарушены.
- Горячий путь не получил новых аллокаций.
- Добавлены/обновлены необходимые тесты.
- Unity resources имеют корректный owner и cleanup.
- Нет новых warnings/errors, относящихся к изменению.
- Diff не содержит случайных scene/package/import правок.
- Документация соответствует фактическому поведению.
- В отчёте перечислены выполненные проверки и оставшиеся риски.

## Формат передачи результата

Отчёт должен быть коротким и проверяемым:

1. Что теперь работает.
2. Какие ключевые файлы изменены.
3. Какие тесты/компиляция/build/profiling фактически прошли.
4. Что не проверялось или осталось ограничением.
5. Следующий логичный шаг, если он действительно нужен.

Не выдавайте план за реализованный результат и не обещайте гарантированный найм. Ценность сдачи доказывается кодом, тестами, измерениями и ясной презентацией.
