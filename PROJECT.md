# Material Accumulation — проектный план

> Статус: production-polish и standalone build проверены; длительный Profiler capture и видео ещё не завершены
> Unity: `6000.3.10f1`
> Render Pipeline: URP 17.3
> Основная платформа демонстрации: Windows, клавиатура

Этот документ — технический источник правды для тестового задания. Он фиксирует не только желаемый результат, но и выбранную модель данных, точную семантику накопления, границы ответственности, критерии проверки и план презентации. Если реализация осознанно отходит от этого документа, решение и причина должны быть добавлены в раздел «Журнал решений».

## 1. Цель и критерий сильной сдачи

Нужно показать не просто деформируемый Mesh, а небольшую законченную инженерную систему:

- накопленный материал хранится независимо от визуального Mesh;
- материал добавляется монотонно: ни движение, ни уменьшение радиуса не могут стереть результат;
- быстрый проход обрабатывается по всему отрезку движения, без кадровых разрывов;
- количество добавленного материала определяется временем воздействия, а не количеством кадров или внутренних штампов;
- повторные и пересекающиеся воздействия работают с одним общим состоянием;
- после прогрева рабочий цикл не создаёт managed GC allocations;
- ядро алгоритма не зависит от `MonoBehaviour`, сцены, ввода и рендеринга;
- ключевая математика покрыта Edit Mode тестами;
- репозиторий содержит понятную историю, инструкцию запуска, результаты профилирования, фактическое время и честные ограничения.

Визуальная аккуратность важна, но приоритеты такие: корректность → измеримая производительность → ясная архитектура → презентация.

## 2. Карта требований

| Требование | Решение | Как проверяем |
|---|---|---|
| Перемещение WASD | Input System на Unity-границе, нормализованный вектор движения | Диагональ не быстрее осевого движения |
| Циклический радиус | Нормализованная `AnimationCurve`, фаза `[0, 1)`, частота в циклах/сек | В Inspector меняются база, амплитуда, частота и кривая |
| Накопление по Space | Один запрос sweep за кадр, только пока ввод активен | Удержание Space меняет высоту, отпускание — нет |
| FPS-независимая скорость | Все пространственные подшаги делят один `deltaTime`; сумма весов равна ему | Один и тот же сценарий при разных разбиениях времени даёт близкий результат |
| Заполнение снизу вверх | Высота ячейки растёт на `fillRate * exposureTime`, но не выше оболочки полусферы | Тест статического заполнения и ограничения оболочкой |
| Сохранение результата | Обновление высоты строго монотонно | Тест: меньшая/сдвинутая зона не уменьшает высоту |
| Непрерывный быстрый след | Отрезок «предыдущее → текущее положение» дискретизируется по размеру ячейки | Тест быстрого sweep и демонстрация при низком FPS |
| Изменяемый радиус вдоль пути | Радиус интерполируется на том же отрезке и тоже ограничивает шаг | След заметно расширяется и сужается без скачков |
| Повторные/пересекающиеся проходы | Все воздействия модифицируют один `HeightField` | Тест повторного и перекрёстного прохода |
| Сброс | `Array.Clear` состояния и полное обновление представления | Клавиша `R` и публичная команда Reset |
| Состояние отдельно от Mesh | Единственный источник истины — `float[]`; Mesh является проекцией | Core-тесты выполняются без сцены и Mesh |
| Нет постоянных аллокаций | Постоянные буферы, value types, dirty region, без LINQ/новых коллекций в цикле | Profiler после прогрева: `GC Alloc = 0 B/frame` |
| Нет объектов-порций | Один height field и один отображающий Mesh | Иерархия сцены не растёт во время рисования |

## 3. Осознанные границы решения

Используется регулярная сетка высот — это прямо разрешено заданием и оптимально для поверхности без нависаний. Для каждой вершины сетки хранится одна высота. Весь материал — одно поле и одна геометрия, а не набор следов, декалей, частиц или объектов.

Главные инварианты модели:

```text
height[i] >= 0
heightAfter[i] >= heightBefore[i]
height[i] изменяется только командой накопления или Reset
Mesh никогда не является источником состояния
```

Мы намеренно не строим универсальный terrain framework, ECS-решение или физическую симуляцию сыпучего вещества. Для тестового это увеличило бы объём и риск, не улучшив доказательство требуемой механики.

## 4. Архитектура и зависимости

Зависимости направлены от Unity-адаптеров к чистому ядру:

```text
Input System ─┐
AnimationCurve├─> BrushControllerBehaviour ─> AccumulationSurfaceBehaviour
Time          ┘                                  │
                                                  v
                                      AccumulationSimulation
                                                  │
                                      HemisphereAccumulator
                                                  │
                                             HeightField
                                                  │ dirty region
                                                  v
                                         HeightFieldMeshView ─> Mesh
```

### 4.1 Core — чистая модель и алгоритм

Сборка `PromVR.MaterialAccumulation.Core` создаётся с `noEngineReferences: true` и не использует `UnityEngine`.

- `GridDescriptor` — размеры, шаг и преобразование координат поверхности в индексы сетки.
- `GridRect` — value type для ограниченной и объединяемой грязной области; умеет представлять пустой результат.
- `HeightField` — владеет заранее созданным `float[]`, предоставляет чтение, контролируемую запись и `Reset`.
- `Sweep` — неизменяемые данные воздействия: начальная/конечная позиция XZ, радиусы и длительность.
- `HemisphereAccumulator` — применяет sweep к `HeightField`, возвращает изменённую область.
- `AccumulationSimulation` — координирует состояние между последовательными кадрами, накопление и reset, если это не окажется лишним после первой реализации.

Интерфейсы добавляются только на реальных границах замены. Для внутренних алгоритмических классов предпочтительны конкретные типы: «SOLID» не означает интерфейс на каждый класс.

### 4.2 Unity Runtime — адаптеры и представление

- `AccumulationSurfaceBehaviour` — composition root поверхности: создаёт Core-состояние, Mesh и view; принимает sweep; освобождает native/Unity-ресурсы.
- `BrushControllerBehaviour` — читает ввод, вычисляет перемещение и радиус, передаёт только числовое воздействие поверхности.
- `HeightFieldMeshView` — создаёт топологию один раз и синхронизирует изменённые вершины/нормали.
- `HemisphereZoneView` — один переиспользуемый визуализатор текущей зоны. Он не хранит материал и не порождает объекты во время работы.

Unity-зависимости заканчиваются в этой сборке. `AnimationCurve`, `Time`, Input System, `Mesh`, материалы и жизненный цикл компонентов не проникают в Core.

### 4.3 Presentation и delivery assets

- `PromVR.MaterialAccumulation.Presentation` содержит только HUD и читает узкий read-only API controller-а. Накопление из UI не вызывается.
- HUD обновляет Image fill и меняет заранее созданные строки только при смене состояния; per-frame форматирования чисел нет.
- HUD переключается между RU/EN без внешнего localization framework. Выбранный язык хранится в `PlayerPrefs`, а при первом запуске определяется по языку ОС.
- Готовая демо-сцена является единственной сценой в Build Settings и собирается стандартным Unity Build Profile.
- Специальные scene builder/build pipeline не поставляются: после фиксации сцены они стали лишней зависимостью от Editor API.
- Simulation и dirty Mesh sync имеют именованные `ProfilerMarker`, чтобы измерять их независимо в Profiler.

### 4.4 Почему состояние не хранится в вершинах

Чтение/запись `mesh.vertices` связывает алгоритм с Unity, смешивает модель с представлением и часто провоцирует копирование массивов. Отдельный `HeightField` даёт:

- тестирование математики без сцены;
- независимый reset, сериализацию и будущую смену renderer;
- явные инварианты и контролируемое изменение;
- возможность позже перенести вычисления в Jobs/Burst или на GPU.

## 5. Модель регулярной сетки

Поверхность задаётся числом quad-ов `resolutionX × resolutionZ` и размером в мировых единицах. Число образцов высоты и вершин:

```text
vertexCountX = resolutionX + 1
vertexCountZ = resolutionZ + 1
heightCount  = vertexCountX * vertexCountZ
index(x, z)  = z * vertexCountX + x
```

Координаты сетки хранятся в локальном пространстве поверхности. На старте допустимы только перенос и единичный scale родительского объекта; либо адаптер явно переводит мировую позицию кисти через `Transform.InverseTransformPoint`. Неявная поддержка произвольного non-uniform scale запрещена: она превращает круг в эллипс и ломает смысл радиуса.

Рекомендуемая демо-конфигурация:

| Параметр | Значение по умолчанию | Причина |
|---|---:|---|
| Размер поверхности | `12 × 12 m` | Достаточно для нескольких проходов |
| Resolution | `128 × 128` quads | `16 641` вершин — хороший баланс формы и CPU |
| Базовый радиус | `1.25 m` | Хорошо читается в кадре |
| Амплитуда | `0.35 m` | Ширина заметно меняется, радиус остаётся положительным |
| Частота | `0.25 cycles/s` | Полный цикл за 4 секунды |
| Скорость движения | `3 m/s` | Удобное управление и показ быстрого следа |
| Скорость заполнения | `0.60 m/s` | Рост виден, но форма не заполняется мгновенно |

Brush ограничивается внутри поверхности с учётом текущего радиуса. Это сохраняет нулевую высоту на внешнем крае и визуально замыкает объём с базовой плоскостью.

## 6. Семантика полусферического накопления

Для образца поверхности `p = (x, z)`, центра кисти `c` и радиуса `r`:

```text
distanceSquared = (p.x - c.x)^2 + (p.z - c.z)^2

если distanceSquared >= r^2:
    образец не затронут

иначе:
    ceiling = sqrt(r^2 - distanceSquared)
    candidate = min(oldHeight + fillRate * sampleTime, ceiling)
    newHeight = max(oldHeight, candidate)
```

Последний `max` — критический монотонный предохранитель. Если накопленная высота уже выше оболочки текущей полусферы, воздействие ничего не делает, а не обрезает существующий материал.

Такое определение означает:

- статичная зона постепенно заполняется снизу вверх до формы полусферы;
- повторное воздействие продолжает незавершённое заполнение;
- пересечения суммируют время воздействия в одном поле;
- полусфера ограничивает только новое добавление;
- материал не может самопроизвольно уменьшиться.

На окружности используется строгое сравнение с небольшим числовым допуском только при необходимости. Дополнительное сглаживание или falloff не вводятся: полусферическая оболочка уже формирует естественный профиль.

## 7. Непрерывный sweep и независимость от FPS

Простое применение одной кисти в текущей позиции оставляет разрывы. Проставление множества полных кистей с `deltaTime` на каждой, напротив, завышает объём в зависимости от количества подшагов. Поэтому sweep дискретизируется одновременно в пространстве и времени.

### 7.1 Число сегментов

```text
positionSegments = ceil(distance(start, end) / maxStampSpacing)
radiusSegments   = ceil(abs(startRadius - endRadius) / maxRadiusStep)
segmentCount     = max(1, positionSegments, radiusSegments)

maxStampSpacing = 0.5 * min(cellSizeX, cellSizeZ)
maxRadiusStep    = 0.5 * min(cellSizeX, cellSizeZ)
```

Радиус и центр линейно интерполируются. Плотность сэмплирования привязана к разрешению представимой геометрии, а не к FPS или произвольному числу штампов.

### 7.2 Временные веса

Для движущегося или меняющего радиус sweep используются точки от `0` до `segmentCount` включительно с трапецеидальными весами:

```text
baseStepTime = frameDeltaTime / segmentCount
endpointWeight = 0.5
innerWeight    = 1.0
sum(sampleTime) = frameDeltaTime
```

Начальная и конечная точки получают половину шага, внутренние — полный. Это включает оба конца пути, но не умножает время воздействия. Для полностью неподвижной кисти применяется один stamp с полным `frameDeltaTime`.

Если Space не удерживается, предыдущее положение и радиус всё равно обновляются. Поэтому новое нажатие не дорисует путь, который кисть прошла в неактивном состоянии.

### 7.3 Ограниченная область вычислений

Каждый stamp перебирает не всю карту, а только AABB диска, переведённый в зажатый диапазон индексов. Изменившиеся ячейки объединяются в один `GridRect`. Никакие списки затронутых ячеек на кадр не создаются.

Оценка стоимости:

```text
O(sum(stamp bounding-box cells))
```

При длинном пути после очень большого кадрового зависания число подшагов сознательно возрастает: это плата за сохранение непрерывности. Искусственный лимит, создающий геометрические дыры, в базовом решении не вводится.

## 8. Обновление Mesh без постоянных аллокаций

### 8.1 Инициализация один раз

- создаётся один runtime `Mesh`, вызывается `MarkDynamic()`;
- vertex/index format выбирается по числу вершин (`UInt16` или `UInt32`);
- индексы треугольников и UV строятся один раз;
- выделяется один постоянный vertex buffer (массив структур или persistent `NativeArray`);
- bounds задаются консервативно: размер поверхности по XZ и диапазон Y от нуля до максимального радиуса `baseRadius + amplitude`;
- Mesh назначается одному `MeshFilter`; материал — одному `MeshRenderer`.

Кривая радиуса трактуется как нормализованная `[0, 1]`, её значение clamp-ится, а итог вычисляется как:

```text
radius = baseRadius + amplitude * (2 * curveValue - 1)
```

Валидация требует `baseRadius > amplitude >= 0`. Поэтому известны безопасные минимальный и максимальный радиусы, а bounds не нужно пересчитывать каждый кадр.

### 8.2 Обновление после воздействия

- пустой dirty rect — Mesh не трогаем;
- позиции обновляются только у реально затронутых образцов;
- область нормалей расширяется на одну ячейку, потому что центральные разности зависят от соседей;
- нормали считаются вручную по градиенту высот в заранее созданном буфере;
- изменённые строки передаются через `Mesh.SetVertexBufferData` с `MeshUpdateFlags` без валидации, пересчёта bounds и уведомлений, которые здесь не нужны;
- topology, UV и индексы повторно не строятся.

Не используются в рабочем цикле:

- `mesh.vertices` / `mesh.normals` как источник данных;
- `RecalculateNormals`, `RecalculateBounds` и `Optimize` каждый кадр;
- LINQ, лямбды, boxing, `new List`, `new array`, строки для debug UI;
- создание или уничтожение GameObject для порций материала;
- изменение `sharedMesh` импортированного asset-а.

Если частичные row-upload вызовы на целевой версии Unity окажутся дороже полной передачи маленькой сетки, решение выбирается по Profiler, а не по предположению. Состояние всё равно остаётся отдельным.

### 8.3 Жизненный цикл ресурсов

Runtime Mesh уничтожается в `OnDestroy`. Persistent native buffer обязательно `Dispose`-ится. Инициализация идемпотентна или защищена от повторного запуска. При domain reload off повторный Play Mode не должен оставлять скрытые Mesh или неосвобождённую память.

## 9. Управление и Inspector

### Обязательные параметры

- `Movement Speed`, m/s;
- `Base Radius`, m;
- `Radius Amplitude`, m;
- `Radius Frequency`, cycles/s;
- `Radius Curve`, нормализованная кривая одного цикла;
- `Accumulation Speed`, m/s.

### Параметры поверхности

- `Size X/Z`;
- `Resolution X/Z`;
- материал накопленной поверхности;
- материал/цвет визуализации зоны.

Все значения валидируются в `OnValidate` и повторно в runtime, потому что данные asset-а могут быть некорректны вне Inspector. Ошибка конфигурации должна сообщаться один раз при запуске, а не создавать log spam.

### Управление демо

| Клавиша | Действие |
|---|---|
| `WASD` | Перемещение зоны по XZ |
| `Space` | Накопление |
| `R` | Полный reset |
| `Esc` | Выход только в standalone build |

Вектор WASD нормализуется перед умножением на `speed * deltaTime`. Ввод читается один раз за кадр. Для тестов Core никакая клавиатура не нужна.

## 11. Стиль C# и объектная модель

- namespace: `PromVR.MaterialAccumulation.Core` и `.Unity`;
- один основной тип на файл, имя файла совпадает с типом;
- `sealed` для компонентов и сервисов, не спроектированных для наследования;
- поля приватные; Inspector-поля — `[SerializeField] private`;
- неизменяемые команды и координатные данные — `readonly struct`;
- зависимости передаются явно через конструктор в Core;
- `MonoBehaviour` используется как адаптер жизненного цикла, не как контейнер доменной логики;
- публичный API минимален и документирует единицы измерения;
- комментарии объясняют причину, инвариант или численный компромисс, а не пересказывают строку кода;
- `Update` короткий: прочитать ввод → вычислить состояние кисти → отправить sweep → синхронизировать view;
- отсутствие ранней микрооптимизации: каждое усложнение горячего пути подтверждается Profiler или очевидным устранением аллокации.

## 12. План тестирования

### 12.1 Обязательные Edit Mode тесты Core

1. `StaticStamp_IncreasesHeightByRateTimesDuration`.
2. `StaticStamp_NeverExceedsHemisphereCeiling`.
3. `LowerCeiling_NeverReducesExistingHeight`.
4. `RepeatedExposure_ContinuesAccumulation`.
5. `OverlappingSweeps_ModifyTheSameHeightField`.
6. `Sweep_CoversFastMovementWithoutCenterlineGaps`.
7. `Sweep_TimeWeightsSumToFrameDuration`.
8. `EquivalentMotion_WithDifferentFramePartitions_IsWithinGridTolerance`.
9. `ChangingRadius_ChangesTrailWidthContinuously`.
10. `StampAtBoundary_DoesNotAccessOutsideGrid`.
11. `Reset_ClearsEveryHeightAndMarksFullGridDirty`.
12. `EmptyOrInactiveSweep_DoesNotChangeState`.

FPS-инвариантность для дискретной сетки проверяется с разумным численным tolerance, а не побитовым равенством: разные трапецеидальные разбиения аппроксимируют один непрерывный процесс.

### 12.2 Интеграционные проверки

- Play Mode стартует без исключений и missing references;
- размер иерархии не растёт при минуте рисования;
- вершины Mesh соответствуют `HeightField` после воздействия и reset;
- preview совпадает по центру и радиусу с данными sweep;
- кисть не выходит за разрешённые границы;
- повторный вход в Play Mode не оставляет runtime Mesh;
- build сцены запускается с клавиатурным управлением.

### 12.3 Производительность

Проверка выполняется в Development Build и в Editor Profiler после прогрева, с отключённым Deep Profile:

- 60 секунд непрерывного движения и накопления;
- максимальный радиус и диагональное движение;
- отдельный прогон при ограничении 10–15 FPS для демонстрации sweep;
- `GC Alloc` рабочего кода: `0 B/frame`;
- нет роста числа GameObject, Mesh и managed heap;
- записываются CPU-модель, разрешение, средний/95-й percentile времени simulation и mesh update.

Числовой CPU-бюджет нельзя честно объявить без целевого железа. После измерения в `README.md` добавляется таблица с конфигурацией машины и фактическими значениями.

## 14. Визуальная подача демо

Сцена должна выглядеть спокойно и профессионально:

- изометрическая камера, вся рабочая область видна;
- нейтральный фон и основание, контрастный материал накопления;
- полупрозрачная или каркасная полусфера показывает текущий предел;
- мягкий directional light и тени подчёркивают рельеф;
- без тяжёлых постэффектов, маскирующих геометрию;
- одна небольшая статичная панель управления допустима, но не ценой per-frame allocations.

Preview — один постоянный объект. Запрет задания относится к порциям материала; всё накопление остаётся одним Mesh.

### Сценарий видео, 60–90 секунд

1. Короткий общий план и Inspector с ключевыми параметрами.
2. Удержание Space без движения: видно заполнение снизу вверх.
3. Движение с меняющимся радиусом: непрерывный след разной ширины.
4. Быстрый проход и пересечение ранее созданного следа.
5. Повторный проход: высота продолжает расти, старое не исчезает.
6. Уменьшившаяся/ушедшая зона не срезает материал.
7. Reset по `R`.
8. Короткий кадр Profiler: `GC Alloc = 0 B/frame`, стабильная иерархия.

Видео лучше записать из standalone Development Build без лишних окон, а параметры и Profiler показать отдельными короткими вставками.

## 17. Основные ограничения базового решения

1. Height field хранит одну высоту на XZ-точку, поэтому не поддерживает нависания, пещеры и отдельные слои.
2. Точность и минимальная представимая кисть ограничены шагом сетки; радиус заметно меньше ячейки будет выглядеть нестабильно.
3. Крутые края аппроксимируются треугольниками регулярной сетки и могут выглядеть угловато на низком resolution.
4. Это визуальная модель накопления, а не физика сыпучего материала: нет осыпания, сохранения объёма при перераспределении и угла естественного откоса.
5. Высота ограничена текущей полусферической оболочкой в момент добавления; материал выше неё сохраняется, но новая масса там не добавляется.
6. CPU-стоимость растёт с площадью кисти, resolution и длиной sweep за кадр.
7. Базовая версия рассчитана на одну кисть на главном потоке. Несколько источников можно применить последовательно к тому же полю, но scheduling не оптимизирован.
8. MeshCollider по кадрам не обновляется: для визуального тестового это лишняя стоимость. Если нужна физика, collider обновляется реже или отдельной упрощённой сеткой.
9. Произвольный non-uniform scale/наклон поверхности не является частью базового контракта без явного преобразования метрики.

Ограничения нужно показывать как осознанные границы модели, а не скрывать.

## 18. Возможные улучшения

В порядке разумной ценности:

1. Разделить поле на dirty tiles и обновлять/рендерить только затронутые чанки больших поверхностей.
2. Перенести rasterization и normals в Burst Jobs с persistent `NativeArray`, сохранив тот же Core-контракт.
3. Добавить adaptive sweep: аналитически находить интервал влияния на ячейку или увеличивать шаг вдали от границ, сохраняя временной интеграл.
4. GPU compute/RenderTexture height map для очень больших сеток; CPU-копию держать только если она нужна gameplay.
5. LOD и clipmap для больших миров.
6. Сериализация/загрузка height field, delta-compression dirty tiles и undo/redo.
7. Несколько типов brush profile через стратегию ceiling function: sphere, cone, custom sampled curve.
8. Детерминированный fixed-step режим для replay/network, отделённый от частоты визуализации.
9. Упрощённый collider, обновляемый по таймеру или по порогу изменения.
10. Editor tooling: preview разрешения, оценка памяти/стоимости, предупреждения о непредставимом радиусе.

Jobs/GPU не должны появляться до профилирования базовой версии: они усложняют сдачу и тестирование, а на сетке около 16k вершин могут быть просто не нужны.
